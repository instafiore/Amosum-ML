# AMOSUM-ML: Instance-Aware AMOSUM Propagator Selection in ASP

> **Automatically selecting the best AMOSUM propagator configuration on a per-instance basis using Machine Learning.**

---

## Overview

Answer Set Programming (ASP) is a powerful declarative paradigm for knowledge representation and automated reasoning, where solutions are encoded as stable models of logic programs. A recurring pattern in real-world ASP problems is the co-occurrence of **SUM constraints** — which assert that a weighted sum of literals meets a given threshold — and **At-Most-One (AMO) constraints**, which restrict the simultaneous truth of elements within a set.

The **AMOSUM propagator** was introduced to jointly handle these two constraint types, achieving significant performance gains over independent treatment. Building on this, several enhanced configurations of the AMOSUM propagator have been proposed — yet no single configuration dominates across all problem instances.

This project addresses that gap with a **Machine Learning-based approach** that automatically selects the most effective propagator configuration for each problem instance, using semantically meaningful features extracted from the interaction between SUM and AMO constraints.

**Key results:** ML-based selectors substantially outperform any single static configuration in both number of solved instances and average runtime.

---

## How It Works

```
Problem Instance
      │
      ▼
Feature Extraction  ──►  SUM × AMO interaction features
      │
      ▼
ML Selector  ──►  Best AMOSUM configuration
      │
      ▼
clingo + AMOSUM  ──►  Solution
```

1. **Feature extraction** — Semantic features capturing the structural relationship between SUM and AMO constraints are extracted from each instance.
2. **ML-based selection** — A trained classifier maps instance features to the predicted best propagator configuration.
3. **Solving** — The selected configuration is passed to `clingo` with the AMOSUM propagator.

## Benchmarks Execution & Data Structure

The training dataset is built from three combinatorial benchmark families, providing diverse coverage of SUM+AMO interaction patterns.

Prior to constructing the datasets, all benchmarks were executed on a cluster using Slurm to gather performance data. The process was split into two phases: first, all the training instances were run, followed by the evaluation (IJCAI) instances. The outputs of these runs were stored in two separate directories: `training_benchmarks_results` and `ijcai_benchmarks_results`.

Due to computational and storage constraints (high volume of generated files), we omit the raw results from the repository. We provide only a single example of the output structure generated by Slurm to serve as a reference: the `config2` configuration for `AMOSUM_GraphColouring` (which corresponds to executing `clingo /GraphColouring/encoding-plain-amo.asp $instance`).

**Required Directory Structure:**
To reproduce the results and execute the scripts located in the `experiments` folder, it is necessary to run the benchmarks and populate the exact directory structure described below. The experiment scripts expect the output statistics to be grouped by benchmark family and then by configuration.

```text
amosum-ml/
├── training_benchmarks_results/     # Results for the training instances
│   ├── AMOSUM_GraphColouring/
│   │   ├── config1/
│   │   ├── config2/
│   │   └── ...
│   ├── AMOSUM_GroupAssignment/
│   │   └── ...
│   └── AMOSUM_Knapsack/
│       └── ...
└── ijcai_benchmarks_results/        # Results for the IJCAI instances
    ├── AMOSUM_GraphColouring/
    │   ├── config1/
    │   ├── config2/                 # (Example included in repository)
    │   └── ...
    ├── AMOSUM_GroupAssignment/
    └── AMOSUM_Knapsack/
```

*Note: To prevent bloated commits, these directories and their contents are ignored by `.gitignore`, except for the single `config2` example.*

## Dataset Construction

Building the full training dataset involves two steps:

### Step 1 — Extract MEASP features and create dataset measp

```bash
python amosum-ml/feature_measp/extract_feature.py
```

```bash
python amosum-ml/dataset_builder/preprocessed/dataset_building_measp_split.py
```

The first script extracts the main Me-Asp features from each instance and the second one creates the preprocessed dataset connected to this extraction.

### Step 2 — Build the complete dataset

```bash
python amosum-ml/dataset_builder/feature_extractor_amosum.py
```

This merges the MEASP features with AMO-specific features and produces the final dataset splits used for training and evaluation.

To train the machine learning models and reproduce all the proposed architectures, you need to run the Jupyter Notebook located in the `training-selectors` directory:

cd training-selectors
jupyter notebook amo-eosum-selectors.ipynb

Execute the cells to train the models and save the `.joblib` files locally.

## Experiments & Evaluation

After training the models and tracking their intrinsic accuracy, the final phase consists of conducting the experiments to compare the dynamically selected ML configurations against the static baseline configurations. This validates the real-world time savings and effectiveness of the automated selection.

We structured the evaluation into 7 distinct experiments to test different machine learning approaches and cascade architectures:

- **Experiment 1 (Standalone XGBoost):** A standard single-model approach where an XGBoost classifier directly predicts the best ASP configuration.
- **Experiment 2 (Simple Cascade - Threshold 0.75):** A two-tier cascade architecture using a Decision Tree for fast, confident predictions (triage) and an XGBoost oracle for harder instances (confidence threshold < 0.75).
- **Experiment 3 (Optimized Cascade):** An enhanced version of the cascade model with optimized hyperparameters for both the triage and oracle components.
- **Experiment 4 (FOLD-R++ Cascade):** A cascade model utilizing FOLD-R++ (an interpretable rule-based machine learning algorithm) alongside standard classifiers.
- **Experiment 5 (AutoML Cascade):** A cascade architecture where the components were discovered and optimized via an Automated Machine Learning (AutoML) pipeline.
- **Experiment 6 (AutoML L1 - Triage Only):** An ablation study evaluating only the first level (triage) of the AutoML cascade independently.
- **Experiment 7 (AutoML L2 - Oracle Only):** An ablation study evaluating only the second level (oracle) of the AutoML cascade independently.

This process is handled by two main scripts located in the `amosum-ml/experiments/` folder:

### 1. `models_performance.py`
This script acts as the main runner. It loads the pre-trained ML models (.joblib) and iterates over the test set instances. For each instance, it queries the model to predict the optimal propagator, constructs the corresponding command, and actually executes `clingo`/`amoclingo` with a timeout, measuring the true inference + solving time.

**How to run it:**
You can specify the experiment ID and the domain (in our case is always AMO). For example:
```bash
# Run experiment 3 (Optimized Cascade) for the AMO domain
python amosum-ml/experiments/models_performance.py --experiment 3 --domain AMO

# Run all experiments 
python amosum-ml/experiments/models_performance.py --experiment ALL --domain AMO
```
*It generates detailed CSV files recording the solving status and runtime per instance.*

### 2. `stats.py`
After capturing the execution times, this script consumes the CSV generated by `models_performance.py`. It calculates the metrics by comparing the ML solving time against the theoretical "Virtual Best Solver" (VBS), counts the successfully solved instances per underlying configuration, and analyzes UNSAT results or misclassifications.

**How to run it:**
Run it with the same experiment IDs used previously:
```bash
# Generate the stats report for experiment 3
python amosum-ml/experiments/stats.py --experiment 3 --domain AMO

# Generate reports for all run experiments
python amosum-ml/experiments/stats.py --experiment ALL --domain AMO
```
*Outputs are comprehensive text reports (`ml_statistics_report.txt`) saved directly inside each experiment's respective directory.*
